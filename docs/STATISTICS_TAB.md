# Требование: вкладка «Статистика сделок» (TRU-6)

Статус: черновик Продукта, v1.
Родитель: TRU-5. Референс: статистика trader-journal (`src/components/statistics`, `src/lib/core/statisticsViewModel.js`).
Ограничения проекта (обязательны): офлайн, ноль рантайм-зависимостей, никаких внешних запросов. Все расчёты — чистые TS-функции в `src/lib/domain/`, графики — свои SVG-компоненты (как `EquityChart`/`LineChart`), без библиотек.

## 1. Цель

Пользователь по своим закрытым сделкам отвечает на три вопроса: «сколько заработал», «почему», «что исправить». Вкладка — читалка поверх журнала: ничего не редактирует, не хранит своих данных.

## 2. Период и фильтры

- **Период** (главный фильтр, чипы в шапке вкладки): `День / Неделя / Месяц / 3 мес / Год / Всё`. Границы — по `dateClose`, календарные (см. `computePeriodStart` референса). Период применяется ко всем блокам сразу.
- **Фильтры-строка под периодом:** направление (`Все / Long / Short`), тег (из `trade.tags`), «только дисциплинированные» (см. §5).
- Фильтры в v1 не настраиваемые, без сохранения состояния между сессиями.

## 3. Блоки вкладки (порядок на экране)

1. **Сводка** — ряд стат-карточек: итоговый P/L, число сделок, винрейт, средний выигрыш / средний проигрыш, профит-фактор, матожидание, макс. просадка по серии сделок (все формулы — из `computeDaySummary` референса, это уже проверенная логика).
2. **Кривая капитала** — свой SVG-спарклайн накопленного P/L за период по закрытым сделкам (без начального капитала: модель `Trade` его не содержит — отличается от референса, где был initialCapital).
3. **Календарь P/L** — месячная сетка как в `StatisticsCalendar` референса: день → сумма, число сделок, зелёный/красный фон. Месяц листается стрелками; зависимая от выбранного периода (при периоде «Год» показывается последний месяц + итог года в шапке).
4. **По killzone** — бар-чарт: колонки killzone (Лондон / Нью-Йорк / Азия / вне зон) с P/L и винрейтом. Killzone **вычисляется** из `dateOpen`, поле в модель сделки не добавляем (см. §5).
5. **По часам и дням недели** — два маленьких бар-чарта рядом (P/L по часу открытия, по дню недели). Тот же источник, что и killzone.
6. **Дисциплина** — % сделок, прошедших предвходовой чек-лист; список нарушений по кодам (сводка референса `aggregateViolationCodes`). Блок виден только когда данные есть (см. §5).
7. **По тегам и инструментам** — таблица-срез: тег/символ → P/L, винрейт, число сделок, отсортировано по P/L.

Блоки 4–7 скрываются, если в выбранном периоде нет подходящих данных (пустая вкладка — только блоки 1–3 с подсказкой «Нет сделок за период»).

## 4. Метрики (полный состав)

Для любого среза (весь период, killzone, тег, символ, час): `count`, `sum(P/L)`, `winrate`, `avgWin`, `avgLoss`, `profitFactor`, `expectancy`, `maxDD` (по серии сделок среза), `best`, `worst`.

## 5. Данные: что есть, чего нет

- Есть в модели `Trade` сегодня: `dateOpen/dateClose`, `pair`, `direction`, `volume`, `profit`, `tags`, `status` — блоки 1–3, 5, 7 строятся сразу.
- **Killzone** — производная от `dateOpen` чистая функция (`src/lib/domain/killzones.ts`, новую логику не выдумывать, перенести идею `primaryKillzone` референса).
- **Чек-листы и нарушения** — в модели `Trade` отсутствуют. Требование к TRU-5/будущей задаче: поле `checklist: { done: boolean, violations: string[] } | null` на сделке, заполняется в `TradeDialog`. До появления поля блок «Дисциплина» не показываем, фильтр «только дисциплинированные» скрыт.
- P/L — в валюте счёта как в журнале; никаких курсов и конвертаций (в референсе был USD/FX-слой — не переносится).

## 6. Реализация (оценка, не часть требования)

`src/lib/domain/statistics.ts` — чистые расчёты (порт `statisticsViewModel`/`computeDaySummary` без dayjs, даты — штатный `Date`); `src/routes/statistics/+page.svelte` — вкладка (навигация уже есть в layout); компоненты — карточка, календарь, бар-чарт по образцу существующих SVG-компонентов. Развитие (не v1): произвольный диапазон дат, настройка видимости блоков, срез по стратегии/сетапу (нет в модели), связь с привычками.

## 7. Проверка соответствия ограничениям

Расчёты локальные, рантайм-зависимостей нет, внешних запросов нет, данные читаются из существующего хранилища журнала. CSP не затрагивается.
